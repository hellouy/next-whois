## 问题清单

### [P1-01] WHOIS HTTP 请求无 SSRF 防护、无 redirect 限制

- **文件**: `src/lib/whois/whois-transport.ts`
- **函数**: `queryWhoisHttp` (L96-133)
- **问题**: `fetch(url, init)` 直接请求 admin 配置的 URL，未调用 `isBlockedHost`，未设置 `redirect: 'manual'`
- **原因**: SSRF guard (`src/lib/ssrf-guard.ts`) 仅用于 `/api/http/check` 和 `/api/ssl/cert`，核心 WHOIS 引擎未引用。`fetch` 默认 `redirect: 'follow'`
- **影响**: Admin 配置的 custom HTTP WHOIS server URL 可指向内网地址（如 `http://169.254.169.254/latest/meta-data/`）。fetch 跟随 301/302 重定向后，响应体直接返回给用户
- **触发条件**: 1) Admin 账户被攻陷；2) Admin 误配 URL 为内网地址；3) 外部 WHOIS 服务器被劫持返回 302 到内网
- **修复建议**: 在 `queryWhoisHttp` 入口对 `entry.url` 调用 `isBlockedHost(new URL(entry.url).host)`；设置 `redirect: 'manual'` 并在每个跳转后重新验证目标 host
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 否（仅增加安全校验，不改变正常 URL 的请求行为）
- **测试方法**: 配置 custom server 为 `http://127.0.0.1:43/test`，验证请求被拒绝

### [P1-02] WHOIS TCP 连接无 SSRF 防护

- **文件**: `src/lib/whois/whois-transport.ts`
- **函数**: `queryWhoisTcp` (L8-53)
- **问题**: `net.connect({ host: resolvedHost, port })` 连接到 DNS 解析后的地址，未调用 `isBlockedHost`
- **原因**: `resolveWithDohFallback(host)` 解析域名但不检查解析结果是否为私有 IP
- **影响**: Admin 配置的 custom TCP WHOIS server host 如果解析到 `127.0.0.1` / `10.x.x.x` / `169.254.x.x`，TCP 连接将直接到达内网服务
- **触发条件**: 1) Admin 配置 custom server host 为指向内网的域名；2) DNS rebinding 攻击（首次解析为公网 IP 通过校验，二次解析为内网 IP）
- **修复建议**: 在 `resolveWithDohFallback` 返回后、`net.connect` 之前，调用 `isBlockedHost(resolvedHost)`；对原始 host 也调用 `isBlockedHost` 防止直接输入 IP
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 否
- **测试方法**: 配置 custom server 为 `127.0.0.1`，验证连接被拒绝

### [P1-03] RDAP fetch 无 redirect 限制

- **文件**: `src/lib/whois/rdap_client.ts`
- **函数**: `tryRdapWithUrl` (L372-402)
- **问题**: `fetch(url, { headers, signal })` 未设置 `redirect: 'manual'`，默认跟随重定向
- **原因**: RDAP baseUrl 来自静态 `CCTLD_RDAP_OVERRIDES` 和 `GTLD_RDAP_BOOTSTRAP`（均硬编码可信 URL），但 fetch 跟随 302 后可能到达内网
- **影响**: 如果某个 RDAP 服务器被劫持或配置了 302 重定向到 `http://169.254.169.254/`，fetch 会跟随。虽然响应体需包含 `ldhName`/`rdapConformance` 才会被采用（降低了数据泄露风险），但 fetch 本身仍构成 SSRF（内网端口探测等）
- **触发条件**: 1) 某个 ccTLD RDAP 服务器被劫持；2) node-rdap fallback 从 IANA bootstrap 获取的 URL 被篡改
- **修复建议**: 设置 `redirect: 'manual'`，对每个 Location header 调用 `isBlockedHost`；或使用 `redirect: 'error'` 直接拒绝重定向（RDAP 规范不要求重定向）
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 极低 — RDAP 规范不要求重定向，少数服务器可能用 301 到新路径，需测试验证
- **测试方法**: 模拟 RDAP 服务器返回 302 到 `http://127.0.0.1/`，验证 fetch 不跟随

### [P2-01] CRON_SECRET 比较不抗时序攻击

- **文件**: `src/pages/api/cron/ping.ts` (L17), `src/pages/api/cron/snipe-probe.ts` (L35), `src/pages/api/cron/tld-scrape.ts` (L208), `src/pages/api/remind/process.ts` (L153), `src/pages/api/admin/process-email-queue.ts` (L33), `src/pages/api/admin/expired-domains-crawl.ts` (L264)
- **函数**: 各 cron 端点的 auth handler
- **问题**: 使用 `authHeader !== \`Bearer ${secret}\`` 字符串比较，非 timing-safe
- **原因**: 代码未使用 Node.js `crypto.timingSafeEqual`（仅 `stamp/verify.ts` 和 `init-admin.ts` 使用了）
- **影响**: 攻击者可通过测量响应时间逐字节猜出 CRON_SECRET。实际利用难度高（需大量精确网络测量，且 Vercel 边缘节点引入噪声），但不符合安全最佳实践
- **触发条件**: 攻击者知道 cron 端点路径并能发送大量请求测量时序
- **修复建议**: 使用 `crypto.timingSafeEqual(Buffer.from(authHeader), Buffer.from(\`Bearer ${secret}\`))`（需先比较长度）。或提取 token 部分后用 timingSafeEqual 比较
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 否
- **测试方法**: 验证正确/错误 secret 的响应时间无统计差异

### [P2-02] 支付 webhook 签名比较不抗时序攻击

- **文件**: `src/lib/payment.ts`
- **函数**: `verifyXunhupayWebhook` (L323-328), `verifyStripeWebhookSignature` (L330-352)
- **问题**: 
  - Xunhupay: `sign.toLowerCase() === expected.toLowerCase()` (L327)
  - Stripe: `signatures.some(s => s === expected)` (L348)
- **原因**: 使用字符串 `===` 比较 HMAC 摘要，未使用 `timingSafeEqual`
- **影响**: 攻击者可通过时序攻击逐字节伪造 webhook 签名，伪造支付成功通知
- **触发条件**: 攻击者能向 webhook 端点发送大量请求并测量响应时间
- **修复建议**: 使用 `crypto.timingSafeEqual(Buffer.from(received, 'hex'), Buffer.from(expected, 'hex'))`，比较前先检查长度
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 否
- **测试方法**: 验证正确/错误签名的响应时间无统计差异

### [P2-03] Stripe webhook 无重放保护

- **文件**: `src/lib/payment.ts`
- **函数**: `verifyStripeWebhookSignature` (L330-352)
- **问题**: 从 `sigHeader` 提取了 `timestamp` (L341) 但未与当前时间比较
- **原因**: 代码提取 timestamp 仅用于构造 `signedPayload`，未检查新鲜度
- **影响**: 攻击者截获一个有效的 webhook payload+signature 后可无限重放，可能导致重复标记订单为已支付。`markOrderPaid` 的原子 `WHERE status <> 'paid'` 提供了幂等保护，不会重复授权，但重放仍会触发不必要的 DB 写入和日志
- **触发条件**: 攻击者通过中间人/日志泄露/浏览器历史获取有效的 webhook 请求
- **修复建议**: 在签名验证通过后，检查 `Math.abs(Date.now() / 1000 - parseInt(timestamp)) < 300`（5 分钟窗口），超出则拒绝
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 否（正常 webhook 在秒级送达）
- **测试方法**: 用 10 分钟前的 timestamp 构造请求，验证被拒绝

### [P2-04] CSP `connect-src * data:` 过于宽松

- **文件**: `next.config.js`
- **函数**: `SECURITY_HEADERS` (L14-28)
- **问题**: `connect-src * data:` 允许浏览器向任意域名发送请求
- **原因**: WHOIS 查询页面需要连接多个外部 API（DNS/RDAP/WHOIS 前端代理），开发者使用了通配符
- **影响**: 如果存在 XSS 漏洞，攻击者可通过 `fetch()` 将用户数据（cookie/localStorage）外传到任意域名，CSP 无法拦截
- **触发条件**: 存在 XSS 漏洞时被利用
- **修复建议**: 将 `connect-src` 限制为 `'self'` + 已知 API 域名白名单（vercel.app, challenges.cloudflare.com 等）。对于动态 WHOIS 查询，通过同源 API 端点代理
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 是 — 需确认所有前端直连的外部 API 域名并加入白名单
- **测试方法**: 构建后检查 CSP 头，验证浏览器 console 无 CSP 违规

### [P3-01] Vercel Lambda fire-and-forget 操作可能被冻结

- **文件**: `src/lib/whois/lookup.ts` (L325, L339, L352, L550, L571, L587, L649, L713), `src/lib/payment.ts` (L275, L297), `src/lib/server/domain-enrichment-db.ts` (L103)
- **函数**: 多处 `void` 调用
- **问题**: 在响应发送后执行异步操作（enrichment 持久化、premium 检测、邮件发送等），Vercel Lambda 在响应发送后冻结事件循环，异步操作可能被挂起直到下次请求唤醒或超时丢弃
- **原因**: Vercel serverless 函数在 `res.json()` / `res.end()` 发送响应后冻结执行。`void promise.catch(...)` 中的异步操作在冻结期间不会执行
- **影响**: 1) WHOIS enrichment 数据可能丢失（不持久化到 DB）；2) Premium 检测结果可能不更新缓存；3) 支付确认邮件可能延迟发送。不影响安全性，影响数据一致性
- **触发条件**: 在 Vercel serverless 环境运行，Lambda 在响应后冻结
- **修复建议**: 对于关键操作（如支付邮件），在 `res.json()` 之前 await；对于 enrichment 等非关键操作，可接受现状（best-effort 模式）。或使用 Vercel `waitUntil` API（如果可用）
- **是否需要数据库修改**: 否
- **是否影响现有功能**: 修复时需确保不增加响应延迟
- **测试方法**: 在 Vercel 生产环境测试 enrichment 持久化率和邮件发送延迟

### [P3-02] getClientIp 信任 x-forwarded-for 首段

- **是否需要数据库修改**: 否
- **是否影响现有功能**: 否

## 审计总结（14 个维度）

### 1. 架构

项目是 Next.js Pages Router 单体应用，部署在 Vercel serverless。
- `src/middleware.ts`: 仅 locale 检测 + HMR 修复，matcher 排除 API 路由
- `next.config.js`: 安全头部齐全（HSTS/CSP/X-Frame-Options/Referrer-Policy/Permissions-Policy），Sentry source map 上传后删除
- `vercel.json`: 6 个 cron + 23 个函数 maxDuration 配置，API 路由有 X-Content-Type-Options + X-Frame-Options
- **架构健康度**: 良好。分层清晰（lib/whois 引擎层 → pages/api 接口层 → pages 前端层），缓存三层（L1 内存 → L2 Redis → L3 PostgreSQL）

### 2. SSRF 防护

- `src/lib/ssrf-guard.ts`: 存在完整的 SSRF guard（`isPrivateHost` + `normalizeIPv4` + `isBlockedHost` 含 DNS 解析），覆盖 IPv4/IPv6/loopback/CGNAT/link-local/metadata 等全部私有地址段
- **覆盖范围**: 仅 `/api/http/check` 和 `/api/ssl/cert` 两个 admin 端点使用
- **未覆盖**: WHOIS TCP (`whois-transport.ts` L28), WHOIS HTTP (L122), RDAP fetch (`rdap_client.ts` L379) — 详见 P1-01/02/03
- **tld-rules.ts**: 有独立 `PRIVATE_IP_RE` (L19-33)，仅用于 admin TLD 规则验证
- **结论**: SSRF guard 实现质量高但覆盖面不足，核心查询引擎是主要缺口

### 3. API 安全

130 个 API 端点，认证覆盖：
- **57 个 admin 端点** (`/api/admin/*`): 全部使用 `requireAdmin`（next-auth session + DB-backed email 检查 + IP rate limit 60/min）— 良好
- **6 个 cron 端点**: fail-closed 模式（CRON_SECRET OR admin session）— 良好（但 timing-unsafe，见 P2-01）
- **3 个 lookup 端点**: tiered rate limit（匿名/登录/API key 分层）— 良好
- **3 个 payment webhook**: Stripe/Xunhupay 本地签名验证 + PayPal 服务器端验证 — 良好（但 timing-unsafe，见 P2-02）
- **公开端点** (`/api/http/check`, `/api/ssl/cert`, `/api/dns/records`, `/api/ip/lookup`, `/api/icp/query`): rate limit only，SSRF guard 保护 — 可接受
- **结论**: 认证覆盖全面，无未认证敏感端点

### 4. 密钥管理

- **环境变量**: 无 `NEXT_PUBLIC_` 前缀的敏感变量（good — 不会泄露到客户端 bundle）
- **CRON_SECRET**: 用于 cron 认证，存储在 Vercel env
- **支付密钥**: Stripe/Xunhupay/PayPal webhook secret 优先从 DB `site_settings` 表读取，fallback 到环境变量 — 良好（支持运行时轮换）
- **NEXTAUTH_SECRET**: 用于 JWT 签名，存储在环境变量
- **Redis/DB 连接字符串**: 通过环境变量配置
- **Sentry auth token**: 仅构建时使用，`deleteSourcemapsAfterUpload: true` 确保 source map 不暴露
- **结论**: 密钥管理规范，无硬编码密钥

### 5. 核心引擎 (lookup.ts, 1531 行)

查询链路：
```
lookupWhoisWithCache → L1/L2/L3 cache → third-party API → lookupWhois
  → parallel: RDAP + WHOIS + DNS probe + premium check + pricing prewarm
  → RDAP first? → grace window for WHOIS enrichment → merge
  → WHOIS first? → grace window for RDAP → merge
  → neither? → fail/error/unregistered
  → retry once on transient failure (jitter 400-800ms)
```

- **超时设计**: RDAP 4s（per-TLD 可调 1-10s），WHOIS 8s（per-TLD 可调 9-12s），outer wrapper 12s
- **grace 窗口**: RDAP 先到→等 WHOIS 400ms；WHOIS 先到→等 RDAP 800ms — 精心调优
- **缓存 TTL**: 智能分级（未注册 300s，已注册到期≤7天 1800s，到期≤60天 3600s，到期≤180天 21600s，正常 43200s，IP/ASN 86400s）
- **SWR**: 剩余 TTL <10% 时触发后台刷新，不阻塞当前请求
- **In-flight dedup**: thundering-herd 防护
- **结论**: 引擎设计成熟，性能优化到位

### 6. 域名解析器

- `toAsciiDomain` / `extractDomain`: 域名标准化，IDN → punycode 转换
- 自定义 punycode 解码器（不依赖 Node.js 弃用的 `punycode` 模块）
- `domainToASCII` from `url` 模块用于 RDAP punycode 推导
- **结论**: IDN 处理完善，近期修复了 IDN ccTLD whois-servers.json 条目（xn--fiqs8s 等 11 条）

### 7. 适配器层 (custom-servers.ts, 698 行)

服务器来源优先级：
```
1. BUILTIN_SERVERS (硬编码 scraper/TCP)
2. DB custom_whois_servers (source='manual' — admin 配置)
3. custom-tld-servers.json (文件)
4. whois-servers.json (静态文件)
5. tld_registry_info (IANA 爬取)
6. GTLD_WHOIS_BOOTSTRAP (1200+ gTLD)
```

- `executeServerEntry` (L488-578): 统一处理 scraper/HTTP/TCP 三种类型
- HTTP: 直接传给 `queryWhoisHttp` — **无 SSRF guard**（见 P1-01）
- TCP: port 43 用 whoiser 库，非 43 用 `queryWhoisTcp` — **无 SSRF guard**（见 P1-02）
- **结论**: 适配器层功能完整但缺少 SSRF 防护

### 8. 缓存

三层缓存架构：
- **L1**: 进程内存 Map，60s TTL，2000 条 LRU eviction — 最快，无网络
- **L2**: Redis（Upstash HTTP 优先 + ioredis TCP 备用），原子 INCR，TTL 由 `computeSmartTtl` 决定
- **L3**: PostgreSQL `whois_cache` 表，仅 Redis 不可用时使用
- **SWR**: stale-while-revalidate，剩余 TTL <10% 时后台刷新
- **In-flight dedup**: Map<string, Promise> 防止 thundering-herd
- **WHOIS rate-limit**: Redis TLD 级限流标记，60s TTL，自动跳过被限流 TLD
- **缓存失效**: `invalidateLookupCacheForTld` 用于 admin 修改服务器配置后清除 L1
- **结论**: 缓存设计精良，三层降级 + SWR + in-flight dedup 是成熟模式

### 9. Serverless

- **Vercel 函数配置**: 23 个函数自定义 maxDuration（10-300s）
- **ESM 外部化**: `whoiser`, `node-rdap`, `ioredis`, `nodemailer` 作为 externals + dynamic import
- **fire-and-forget 风险**: 多处 `void` 调用在响应后执行（见 P3-01），Vercel Lambda 冻结可能导致丢弃
- **长 cron**: tld-scrape 和 snipe-probe 300s maxDuration（见 P3-03）
- **区域**: 仅 `iad1`（美东），所有函数同区域
- **结论**: Serverless 适配合理，fire-and-forget 是已知 trade-off

### 10. Cron

6 个 cron 端点：
| 端点 | 频率 | maxDuration | 认证 |
|------|------|-------------|------|
| /api/cron/ping | 每天 0:00 | 10s | CRON_SECRET OR admin |
| /api/remind/process | 每天 9:00 | 60s | CRON_SECRET OR admin |
| /api/admin/process-email-queue | 每天 2:00 | 60s | CRON_SECRET OR admin |
| /api/cron/tld-scrape | 每天 3:00 | 300s | CRON_SECRET OR admin |
| /api/admin/expired-domains-crawl | 每天 5:00 | 60s | CRON_SECRET OR admin |
| /api/cron/snipe-probe | 每天 9:00 | 300s | CRON_SECRET OR admin |

- **认证模式**: fail-closed（无 CRON_SECRET 时仅 admin session 可触发）— 良好
- **timing-unsafe**: 全部使用 `===`/`!==` 比较（见 P2-01）
- **结论**: Cron 认证设计正确，需修复 timing-safe 比较

### 11. 数据库

- **连接池**: `src/lib/db.ts` (1069 行) 管理 PG 连接池
- **参数化查询**: 全部使用 `$1, $2, ...` 参数化，无字符串拼接 — 无 SQL 注入风险
- **事务**: `withTransaction` 封装，`markOrderPaid` 使用原子 `UPDATE...WHERE status<>'paid'` 实现幂等
- **金额验证**: webhook 回调金额与 DB 订单金额比较，容差 0.01
- **表结构**: rate_limit_records, custom_whois_servers, payment_orders, payment_plans, site_settings, tld_registry_info, tld_fallback_stats, domain_enrichments, whois_cache 等
- **结论**: 数据库操作安全，参数化查询 + 事务 + 幂等设计

### 12. 性能

- **并行查询**: RDAP + WHOIS + DNS probe + premium check + pricing prewarm 同时启动
- **预编译**: whoiser/node-rdap 模块在模块加载时预热（`void import("whoiser").catch(() => {})`）
- **DNS 预热**: `warmupDnsCache` 预解析常用 WHOIS 服务器
- **RDAP bootstrap**: 1223 条静态 gTLD + 130+ ccTLD override，避免运行时 IANA bootstrap 查询
- **per-TLD 超时**: 已知慢服务器（.hu/.jp/.br/.ar 等）独立配置更长超时
- **结论**: 性能优化到位，无明显瓶颈

### 13. 边缘情况

- **无服务器 TLD**: `.hm/.aq/.bv/.sj/.eh/.tf/.pm` 跳过 WHOIS/RDAP 直接到 DNS probe
- **IDN 处理**: punycode 标准化缓存 key，中文/阿拉伯文/西里尔文 TLD 支持
- **rate-limit 检测**: `isWhoisRateLimited` 扫描前 30 行 raw response 匹配 429/limit/quota 模式
- **IANA fallback 检测**: `isIanaFallback` 识别 IANA bootstrap 页面
- **policy banner**: `isPolicyBannerOnly` 识别只返回 usage banner 的限流响应
- **RDAP 404**: 区分 RDAP 服务器 404（域名不存在）vs IANA bootstrap 404（TLD 无 RDAP 服务）
- **registry status**: `registry-reserved`/`registry-premium`/`prohibited` 等特殊状态不被误判为未注册
- **结论**: 边缘情况覆盖全面

### 14. 功能差距

- **无 Vercel `waitUntil`**: fire-and-forget 操作未使用 Vercel 的 `waitUntil` API（如可用），可考虑引入
- **无 request ID / trace ID**: 日志缺少请求级追踪标识，排查问题时依赖时间戳匹配
- **无 API 端点 inventory 文档**: 130 个端点无集中文档，审计需手动扫描
- **无自动化安全测试**: 缺少 SAST/DAST 工具集成，安全检查依赖人工审计
- **CSP connect-src**: 使用通配符 `*`，未按最小权限原则配置（见 P2-04）
- **结论**: 功能差距主要是运维和流程层面，非代码安全问题
