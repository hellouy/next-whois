### 核心审计报告：代码库健康度极低

基于对最新分支（SHA: `b6c104d` 及相关近期提交）及 CI/CD 流水线的分析，RepoMind 对 `next-whois` 的当前状态评估为 **红色警报**。你现在的开发路径是典型的“功能过载”，代码库正在从一个专业的域名工具迅速转变为一个“不可维护的 UI 大杂烩”。

### CI/CD 崩溃分析
- **致命问题**：所有的 CI 工作流（`CI` 和 `Docker Image CI`）全部失败。这意味着你的主分支 `main` 处于**不可部署状态**。任何在该分支上的新增功能都是在“屎山”上叠加，徒增后续修复难度。
- **Replit Agent 的盲点**：Replit Agent 沉迷于添加 UI 特性（广告栏、OG 预览、品牌 stamps），但它似乎没有能力处理 CI 的构建配置错误。不要让它继续添加新页面，直到 CI 变绿。

### 严重缺陷与技术债

1. **解析器的逻辑碎片化**
   - 尽管最近的提交添加了大量功能，但 `src/lib/whois/common_parser.ts` 依然是一个巨大的函数，且缺乏单元测试。当某个 TLD 注册局微调了 WHOIS 格式，整个系统就会在没有任何预警的情况下解析失败。
   - **优化方向**：为 `common_parser.ts` 编写至少 20 个关键 TLD 的测试用例（使用 `vitest`）。

2. **数据库与连接池的“死亡循环”**
   - CI 日志提示数据库连接超时频繁。你正在频繁使用 `runMigrations()` 和各种 `api/admin/*` 的数据库查询。如果数据库连接池没有被正确重用（特别是在 Vercel 的 Serverless 环境下），冷启动将导致严重的性能抖动。
   - **优化方向**：在 `src/lib/db.ts` 中强制使用全局单例池，并确保 `migrate.js` 仅作为离线部署脚本运行，绝对不要在 API 请求路径中初始化迁移。

3. **UI 组件导致的水合错误 (Hydration Mismatch)**
   - 广告组件 `ResultTextAd` 和公告组件 `AnnouncementBanner` 直接读写 `localStorage` 或 `siteSettings`，这在 Next.js 的服务端渲染中极易引发水合错误（客户端与服务端渲染出的 DOM 树不同步）。
   - **优化方向**：确保所有依赖 `localStorage` 或 `window` 的组件都包装在 `useEffect` 中，且组件的初始渲染状态（如 `useState(null)`）不会输出到 SSR 的 HTML 中。

### 功能与用户体验优化清单

#### 1. 页面与结构建议
- **后台管理系统过度膨胀**：你现在有接近 15 个后台管理页面。这已经不再是一个简单的域名查询工具，而是一个完整的 SaaS 后台。
    - **改进**：将后台入口统一，使用侧边栏导航，而不是在 `admin/` 目录下塞入成堆的独立页面。
- **缺失功能**：
    - **Whois 解析监控看板**：你添加了查询失败统计，但缺乏“自动重试”和“报错上报”的闭环。建议集成简单的日志服务（如 Sentry 或自定义的简单的 `Error Log` 表）。
    - **缓存透明度**：当前的缓存 TTL 是自适应的，用户并不知情。在结果页底部显示“数据已缓存 X 分钟，如需最新数据请点击刷新”是一个极佳的 UX 提升。

#### 2. 代码库瘦身建议 (Replit 操作指南)
要求你的 Agent 执行以下动作：
- **重构 UI 逻辑**：将 `src/pages/[...query].tsx` 中超过 500 行的 UI 组件拆分到 `src/components/query/`。现在这个文件太庞大，任何 UI 修改都可能误伤 WHOIS 解析的核心逻辑。
- **测试覆盖率**：不要再写新页面了。要求 Agent 为 `src/lib/whois/lookup.ts` 生成 5 个集成测试，确保解析流在 `RDAP 成功`、`WHOIS 成功`、`都失败` 和 `yisi Fallback` 四种场景下都能稳定运行。
- **API 鉴权合并**：现在的鉴权逻辑（`requireAdmin`, `enforceApiKey`, `checkRateLimit`）分散在每个 API 文件中。要求 Agent 创建一个**中间件层**，统一在请求入口处处理所有的校验，而不是在每个 API 路由中重复编写 `if (!isAdmin) ...`。
